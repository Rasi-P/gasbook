Minimal Product & Inventory implementation

SCOPE
One Products & Inventory admin page, one Accessories tab alongside the existing
cylinder catalog, mixed items in the existing cart/checkout, and item details in
the existing booking/delivery/history/receipt screens. No service appointments,
technicians, separate commerce orders, accessory checkout, separate payments,
returns system, suppliers, warehouses or additional dashboards.

CLEANUP / PRESERVATION
Both main working trees were clean on arrival: the user had already removed the
previous commerce UI, endpoints and implementation files. No working changes
were discarded. Existing Booking, Delivery, Sale, Payment, Direct Sale, cylinder
pricing/stock, cancellation/refund and staff-ownership rules remain in place.
Cylinder-only customer checkout retains its existing behavior.

The database inspection contradicted the prompt: core.0014_commerce_catalog_orders
was ALREADY APPLIED in development (database gasbook, db:5432 inside
gasbook-backend-1). Its source had been deleted. The original Migration operations
and dependency were recovered from its surviving Python bytecode and serialized
with Django MigrationWriter. They were not replaced by a different 0014 schema.
The old commerce order, line and service tables were empty at inspection.

MIGRATION (GENERATED, NOT APPLIED TO DEVELOPMENT)
0015_minimal_booking_inventory depends on the restored 0014. It adds BookingItem
and a nullable booking reference on ProductMovement. A state-only operation retires
CommerceOrder, CommerceLine, ServiceOffering and the movement's old order relation
from the active Django models. Existing tables, columns and historical migrations
are retained physically. There is no historical transaction backfill or repricing.
A read-only migration guard refuses retirement if old commerce orders/lines exist.

Product, ProductCategory and ProductMovement reuse the existing 0014 tables.
Category is entered as simple text on the product form, without a category module.
SKU and old threshold columns remain compatible with the existing schema but add
no new UI/workflow. BookingItem snapshots preserve names, item type/reference,
quantity, rate, amounts and cylinder deposit/refill components. The first cylinder
line owns the unique checkout retry reference; no Booking/Sale schema is duplicated.

API
GET/POST /api/products/
GET/PATCH /api/products/:id/
POST /api/products/:id/stock/ — +1, -1 or explicit quantity, reason, retry UUID
GET /api/products/:id/movements/ — admin-only paginated audit history
POST /api/bookings/preview/ — existing endpoint extended for accessory IDs
POST /api/bookings/checkout/ — creates ONE ordinary mixed Booking atomically
Existing booking, delivery, staff history, customer history, customer ledger,
Sale serialization and /api/receipts/booking/:id/ now include saved accessory lines.
Existing assignment, acceptance, decline, start, completion and rejection routes
remain the lifecycle. There is no new staff order queue.

PRICING / FINANCIALS
New cylinder = (configured deposit + configured/customer-agreed refill) × quantity,
minus existing authorized discounts on the refill component only.
Refill = configured/customer-agreed refill × quantity minus existing discounts;
no deposit. Accessory = configured selling price × quantity; no cylinder discount.
One combined Booking total is the sum of saved net lines. Signed customer-bound
previews require review again if configured prices change before confirmation.
Client-supplied prices/totals and duplicate lines are rejected.
Delivery preserves snapshots and creates one existing Sale/payment set. Only real
cylinder lines create SaleItems; accessory amounts stay on BookingItems. Reports,
customer balances and financial integrity count the combined Sale exactly once.
Existing Direct Sale void/refund rules remain unchanged; booking sales retain their
existing prohibition on direct-sale voiding. No new return/refund workflow was added.

STOCK
On-hand stock is displayed to admins; customer responses expose only availability.
Checkout reserves accessories under sorted PostgreSQL row locks. Completion reduces
on-hand and reserved amounts together. Admin rejection releases reservations.
Staff decline preserves reservations while the booking awaits reassignment.
Admin adjustments cannot reduce on-hand below reserved quantities or below zero.
Retry keys and locked terminal booking transitions prevent duplicate orders,
adjustments, deductions and releases. Each stock change records actor, source,
reason, timestamp and before/after balances. Cylinders still use their existing
location-specific filled/empty stock. Mixed cylinder types collect empty returns
separately within the existing delivery form.

UI
Admin: compact inventory table with image, type, price, stock +/- controls, explicit
quantity setting, edit/activate, and stock movements on the same page. Cylinder
stock/rates stay in their existing controls.
Customer: All Products / Gas Cylinders / Accessories with dynamic counts; images,
description, quantity and availability. Existing mobile/desktop cart and checkout
are extended. Accessories require a cylinder in the same booking.
Staff/admin/customer: shared saved-line components in existing detail/history
screens. The existing receipt template and PDF path include the same saved lines.

DEVELOPMENT DEMO DATA
Five [DEMO] accessories were added to the positively verified development database:
regulator, two-burner stove, LPG hose, hose clips and replacement burner. Each has
an illustrative price/stock, a bundled generated PNG and an initial stock movement
attributed to the existing admin. Existing products/customer/business rows were
not modified. Images were opened and verified after seeding. No migration ran.

Repeatable command, from gasbook:
  docker exec -e GASBOOK_ENV=development gasbook-backend-1 python manage.py seed_accessories --database-name gasbook --actor admin
It skips existing DEMO SKUs, requires DEBUG=True, an exact database-name match,
a local development target and an existing active admin, and refuses QA. It supports
the already-applied 0014 catalog columns as well as 0015; it never migrates.
Image source files and exact prompts: backend/core/demo_products/IMAGES.txt.
Built-in imagegen generated the five PNGs, copied into core/demo_products;
runtime copies are under backend/media/product-images (gitignored).

ACTIVATION / LIMITS
0015 has NOT been applied to development. ACCESSORIES_ENABLED remains false until
migration approval/application and feature activation. Demo rows already exist,
but the new booking feature is not enabled on the running development backend.
Compose startup no longer implicitly migrates or seeds; no service was restarted.
Accessories are sold with a cylinder booking only. Fulfilment remains whole-booking.
No automatic reservation expiry or post-delivery returns workflow was introduced.
The retired commerce tables intentionally remain, preserving applied history.

TEST COMMANDS
From gasbook/backend, use gasbook.test_inventory_settings, which ignores the normal
DATABASE_URL and permits only SQLite memory or a localhost inventory_test database:
  INVENTORY_TEST_DATABASE_URL=postgres://postgres:<test-password>@127.0.0.1:55439/inventory_test .venv/bin/python manage.py test core.tests --settings=gasbook.test_inventory_settings --noinput
The opt-in browser test requires production previews on 5192 (customer) and 5193
(admin/staff), then the same command with RUN_INVENTORY_BROWSER=1 and test label
core.tests.test_product_browser. Every API request is routed to Django's disposable
live test server, never development. No browser/API dependency was added.

Two pre-existing test fixtures had stale trusted refill rates; their fixture rates
now match their submitted/expected rates. The 0012 refusal test wraps its rollback
attempt in a transaction to preserve later test migrations on rejection. Production
0012 and all existing pricing/void logic were not changed by those test corrections.
